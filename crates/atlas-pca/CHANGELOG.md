# Changelog

## Unreleased (0.5.0)

- **BREAKING (security default): provenance by default.** `authorize` runs check `provenance_flow` on every call: a sensitive action (not read-only, or not described) whose choice or arguments do not derive from the principal is refused as an escalation (`provenance_flow: escalate: <reason>`, admitted only by a principal-signed escalation answer); a forged or malformed provenance bundle is a deny (`provenance_flow: <code>: <reason>`). The only opt-out is the grant's signed envelope member `provenance: {mode: "insecure_off"}` (`not-enforced`). New `atlas_pca::arg_provenance`: `decide_arg_provenance`, `prov_leaves`, `occurs_as_token`, `is_read_only_action`, `prov_envelope_error`, `prov_receipt_wire_error`, `prov_action_info_error`, `is_prov_mediator_pin`, `prov_action_digest`, `prov_receipt_ref`, `read_provenance_bundle`, `encode_provenance_header`, and the mediator side `ProvenanceRecorder` (`principal`, `tool`, `retrieval`, `web`, `for_action`; post-quantum and hybrid suites through `with_suite`) with `principal_direct_provenance`. `AuthorizeInput` gains `provenance_mediators`, `provenance_actions`, `provenance_observed`, `provenance`, `provenance_bundle`, `provenance_header`, `provenance_body`; `AuthorizeOptions` gains `with_provenance_mediators`, `with_provenance_actions`, `with_provenance_observed`, `with_provenance_bundle`; the axum guard reads the `PCA-Provenance` header and the `pca_provenance` body member, and `middleware::authorize_request_provenance` takes the header framework-free. `mint_grant` accepts the envelope member `provenance`. Replays `arg-provenance-vectors.json` (every section) and reproduces the reference recorder byte for byte.
- **New: undo windows (verification layer).** `atlas_pca::undo`: `compensation_digest`, undo tokens (`sign_undo_token`, `undo_token_check`, `encode_undo_token`, `decode_undo_token`, `undo_token_digest`), receipts (`sign_undo_receipt`, `verify_undo_receipt`, `undo_receipt_digest`, `undo_receipt_chain_error`), `undo_transition` and `resolve_undo_window`; the obligation kind `undo_window {id, window_end}`. `AuthorizeInput::undo` / `AuthorizeOptions::with_undo` add an optional admission hook: an unanswered escalation that is not a provenance escalation runs under a veto window when the hook returns an admission (only after the window is durably opened); `AuthorizeResult` gains `undo` and `obligations`. Replays `undo-vectors.json`.
- **New (feature `axum`):** `atlas_pca::protect::{protect, ProtectOptions, Protected, Revoker}`: the secure defaults for an axum resource server in one call (grants from a list or function, in-memory replay store, revocation with a `revoker.revoke(id)` handle, `plan: single-step`; your options win; `.tune` adjusts `AuthorizeOptions`). No catalog risk (the TypeScript `protect()` has one). A runnable `examples/axum-server` (its own workspace, not in the published crate) with an end-to-end test.
- **New:** `explain_refusal(reason)` returns `RefusalHelp { check, meaning, fix, docs }` for a refusal reason (same table as the TypeScript `explainRefusal`); never panics.
- **Changed (additive):** denial bodies from the axum guard (`GuardResult::json_body`) gain a `doc` member, the page that explains the refusal. Reasons and every other member are unchanged.
- **New (native signing, agent side):** `atlas_pca::agent`, the producer half of the crate, so an agent never needs a TypeScript process: `KeyPair`, `mint_grant` (envelope, salted goal commitment, `holder_pq`), `delegate` / `attenuate` (append-only caveats; `sealed_caveat`, `max_uses_caveat`, `needs_discharge_caveat`), `plan_commit` with Merkle proofs, `build_pcactn` (signed `aud`/`iat`/`exp`/`nonce`, optional signed slots), `pca_headers`, `sign_escalation_answer`, `sign_discharge`, `sign_narrow`, `issue_passport` / `sign_passport`, `sign_workflow` / `sign_step_receipt`, `sign_read_grant`, `sign_aggregate_grant`, `sign_fresh_at` and the `Agent` client (`act`, `delegate`, `use_plan`: counter, nonce and header handling). ML-DSA-65 / ML-DSA-87 (`fips204`) and SLH-DSA-SHA2-128f / 256s (`fips205`) and the hybrid and nested-hybrid suites sign through `PqKeyPair` and `Suite`; the cargo feature `fndsa-sign` adds FN-DSA-512 / 1024 signing (`fn-dsa-sign`); LESS is verify-only (`unsupported_suite`). Deterministic outputs reproduce `producer-vectors.json` byte for byte (`tests/agent_producer.rs`, which also round-trips every artifact through the verifier).

- **New (K5, workflow admission inside `authorize`, C-308):** `AuthorizeInput::workflow` (`WorkflowGate { principal, rs_signer, required }`, the keys this server pinned) and `workflow_call` (`WorkflowCall { commitment, receipts, step, units, goal_digest }`); `AuthorizeOptions::with_workflow` + `run_workflow`. - **New (K5, workflow gate in the axum guard):** `GuardConfig` carries the gate through `AuthorizeOptions::with_workflow`; the request's step comes from `GuardConfig::with_workflow_step(|parts, body| ...)`, else the JSON body member `workflow` (`{commitment, receipts, step, units, goal_digest}`; a present but malformed member is refused, not ignored), else none. Same refusals as `authorize` (403, `workflow: edge_relation (step pay)`, required and absent 403). Gate order in `authorize`: a required step that is absent is refused BEFORE the PCActn is read; an undecodable PCActn is never judged by the gate and is refused 401, check `pcactn`, reason `undecodable PCActn: ...` (was check `wire`, `wire: PCActn could not be decoded`). Tests: `tests/middleware_workflow.rs`.

## 0.4.1 - 2026-10-12

## 0.4.0 - 2026-10-11 (BREAKING)

- Depth / strict digests (security, parity): every protocol digest the verifiers compute (hop body digest, parent capability hash, caveat comparison, root-vs-grant, root `trusted_root` match, Merkle leaves; new public `hash_canonical_strict`) now uses the STRICT canonical form like the reference (`hashCanonical` is `canonicalizeStrict`): depth <= 32, safe integers, plain decimals. It was the lenient form, so a correctly SIGNED hop carrying a depth-33 value, `1e300` or `2^53+2` verified although the reference refuses the chain; now `hop N: malformed body`. `merkle_root` errs on an out-of-profile leaf. A caller-built hop deeper than the cap is measured iteratively BEFORE the body is cloned (a recursive clone of a 1,000,000-deep value overflowed the stack and aborted the process). `hash_canonical` / `cap_hash` / `params_digest` stay lenient (content addressing only).
- R6-01 (security): the tower/axum middleware's body mode parses the `{"pcactn": ...}` envelope with the strict profile (new `strict_parse_envelope`; depth cap `MAX_JSON_DEPTH` over the whole envelope, as the reference's `defaultExtract`) instead of `serde_json::from_slice`: duplicate keys anywhere are refused, as in header mode (a lenient parse collapsed them last-wins before verification).
- R6-03/R6-04 (parity): `verify_threshold_share` validates the WHOLE signer set like the reference (unknown or wrong-case roles, malformed keys, empty / null / short `pq_pk` anywhere, one key per role, one role per key, a duplicate (role, key) only with the same `pq_pk`); `t` must be 1, 2 or 3 (0..=255 was accepted); `share.role` is required. New `signer_set_hash_b64u`.
- R6-05 (robustness): `verify_chain` applies the reference per-hop type check (`id`/`issuer`/`holder`/`body_digest`/`sig` strings; `alg`/`pq_pk`/`pq_sig`/`holder_pq`/`parent` absent or strings; caveats objects with a string `type`): correctly SIGNED but ill-typed hops (numeric caveat, caveat without `type`, numeric `holder_pq`/`holder`, object `caveats`) and a hop with a numeric `pq_pk` were accepted. No public verify entry point panics on the shared `malformed` vectors.
- R6-02 (security): a signer-set role that registers a `pq_pk` now REQUIRES a PQ (pure or hybrid) threshold share; an ed25519-only share for that role is refused, so an Ed25519 break no longer forges a hybrid-registered role (parity with the TypeScript reference). Corpus: `agent-bound-signerset-with-pq-pk` is now `valid:false`; new positive `agent-hybrid-signerset-with-pq-pk`.
- R5-A1 (security): threshold-share verification is now signer-set PINNED, no longer self-vouched. The share must be for the one key the signer set registers for its role, a PQ/hybrid share verifies only under the set's registered `pq_pk` (a differing share `pq_pk` is refused), the share-suite tag is part of the signed bytes (a classical share cannot be relabelled hybrid), and the signer-set hash now includes a registered `pq_pk` (parity with the TypeScript reference). New corpus vectors: `agent-not-in-signer-set`, `agent-bound-signerset-with-pq-pk`, `agent-hybrid-relabel-*`.

- Suite policy defaults documented: no list = no restriction, an empty list refuses everything, and the hosted API defaults to ed25519 + Ed25519 hybrids (README lists the exact list to pass offline).

- BREAKING (security, R4-01): the standalone chain verifier now takes a non-ed25519 root's PQ authority from the verifier, exactly like the TypeScript reference (R3-01). `verify_chain_policy` gains two trailing arguments, `pq_pins: Option<&HashMap<String, String>>` (root issuer, Ed25519 base64url, to its ML-DSA public key) and `trusted_root: Option<&Value>` (the verifier's own stored root capability). A pure `ml-dsa-65` or hybrid ROOT hop is accepted only if `trusted_root` has the same content hash as the root, or `pq_pins` has an entry for `root.issuer` equal to the root's `pq_pk` (a differing pin is a refusal). Otherwise it is refused with `hop 0: root suite '<alg>' needs a PQ key pinned for the root issuer (policy.pqPins) or the verifier's stored grant (policy.trustedRoot); the root's own pq_pk proves nothing about who issued it (R3-01)`. Before, an attacker-minted root naming a victim Ed25519 issuer, signed with the attacker's own ML-DSA key, verified. Migration: callers of `verify_chain_policy` on a root they did not load from their own store pass `Some(&pins)`, or `Some(&stored_root)`, else `None, None`; `verify_chain` (two arguments) keeps its signature but now refuses every non-ed25519 root. Ed25519 roots are unaffected. `verify_pcactn_core*` is unchanged in behaviour (it passes its grant as `trusted_root`). Internally one `pinned::resolve_pq_key` choke point mints the only key type the suite verifier accepts, so PQ verification cannot be reached with a `pq_pk` read off the artifact.

- BREAKING (security, R3-03): hop and leaf signatures under `ml-dsa-65` / `hybrid-ed25519-ml-dsa-65` are now accepted only if `pq_pk` hashes to the signer's committed `holder_pq` (hop `holder_pq` is now part of the wire format and the signed hop body). Unbound or attacker-supplied PQ keys are rejected, exactly like the TypeScript reference. New `verify_pcactn_core_policy` / `verify_pcactn_json_policy` / `verify_chain_policy` take an optional allowed-suites list (`None` = none, `Some(&[])` refuses everything).
